     Docs summary (to deliver in chat after edits)

     - Auth: Authorization: Bearer <token>. Base https://task-api.cashmine.io,
       /v1 prefix.
     - Endpoints: GET /v1/balances → {asOf, items[{asset, decimals, available, 
       pending, claiming, usdPrice}]}, snapshot recomputed every 15 s. GET 
       /v1/activity?limit(1–20)&cursor → {items[{id,type,asset,amount(signed),st
       atus,exchange|null,createdAt,relatedId|null}], nextCursor|null}. GET 
       /v1/claim-options?asset= →
       {asset,minAmount,fee,destinations[{id,label}]}. POST /v1/claims (header
       Idempotency-Key 1–100 chars; body {asset,amount,destinationId}) → 201
       claim / 200 replay. GET /v1/claims/{id} → claim {id,asset,amount,fee,rece
       iveAmount,destinationId,status,failureReason,createdAt,updatedAt}.
     - Amounts: decimal strings, never numbers; regex ^(0|[1-9]\d*)(\.\d+)?$; ≤
       decimals places. Invalid: .5, 1., 05, 1e-3.
     - Claim rules: minAmount ≤ amount ≤ available (available checked live, not
       snapshot); ≤ decimals places; receive = amount − fee; min/fee per asset
       from claim-options (not fixed).
     - Statuses: claim pending → completed | failed (~20 s); failed returns
       amount to available with failureReason. Submitted amount leaves available
       at once → claiming; snapshot may lag up to 15 s.
     - Idempotency: same key+body → original claim, 200, Idempotent-Replayed: 
       true; same key, different body → 409 IDEMPOTENCY_MISMATCH.
     - Errors: {error:{code,message,field?}}; 400 VALIDATION, 401 UNAUTHORIZED,
       404 NOT_FOUND, 409 IDEMPOTENCY_MISMATCH, 429 RATE_LIMITED (retryAfterMs /
       Retry-After s), 500/503 SERVER, 504 TIMEOUT (outcome unknown).
     - Gaps (→ Assumptions): fee ≥ amount not addressed (client will also
       require amount > fee); no list-claims endpoint (track own claim ids
       locally / via activity relatedId); fee/min decimals vs asset decimals
       unspecified; numeric rate limits unstated; "Max" uses snapshot available,
       server may reject if stale.

     Domain rules (AGENTS.md text)

     - Amounts are strings at API boundary; in app parse to BigInt minor units
       using asset decimals; never Number/parseFloat for money.
     - Input valid iff matches ^(0|[1-9]\d*)(\.\d+)?$, ≤ decimals places, ≥
       minAmount, ≤ available, > fee.
     - receive = amount − fee; show both before confirm. Min/fee/destinations
       always from /v1/claim-options, never hardcoded.
     - Every claim submit carries Idempotency-Key; generate once per confirmed
       intent, reuse on retry of same body; new key only for new intent.
     - Pending intent {key, asset, amount, destinationId} persisted in
       localStorage before POST, until claim id known. After reload with a
       pending unknown intent: offer "Check status / Retry" with the SAME key,
       never a new one.
     - POST outcome unknown = network error, abort/timeout, 500, 503, 504 →
       same-key retry is safe (idempotent). 4xx with definite code (VALIDATION,
       409 IDEMPOTENCY_MISMATCH, …) = definite: show message, keep form.
     - USD total in BigInt too: amount minor units × usdPrice parsed to
       fixed-point BigInt; round once at end for display. No parseFloat/Number
       on money, USD included.
     - Poll GET /v1/claims/{id} until completed|failed; show failureReason.
     - Balances are 15 s snapshots; show asOf.
     - 429: wait retryAfterMs before retry.

  Docs summary

  - Auth: header Authorization: Bearer <token>. Base URL
    https://task-api.cashmine.io/v1. CORS is open; the API accepts the
    Idempotency-Key header and lets the browser read Retry-After and
    Idempotent-Replayed.
  - Endpoints:
    - GET /balances → {asOf, items[{asset, decimals, available, pending, 
      claiming, usdPrice}]}, a snapshot recalculated every 15 s.
    - GET /activity?limit=1..20&cursor= → signed amount, nextCursor is null on
      the last page.
    - GET /claim-options?asset= → {minAmount, fee, destinations[]}.
    - POST /claims → 201, or 200 for a repeated request.
    - GET /claims/{id}.
  - Amount format: decimal strings, never numbers, matching
    ^(0|[1-9]\d*)(\.\d+)?$, with at most decimals places. Fewer places are fine
    ("50.12" with 6).
  - Claim rules: minAmount ≤ amount ≤ available, where the server checks
    available live, not against the snapshot. At most decimals places. You
    receive amount − fee. Minimum and fee are set per asset, not fixed.
  - Statuses: pending → completed | failed within about 20 s. On failure the
    amount goes back to available, with a failureReason. A new claim leaves
    available at once and moves to claiming; the balances snapshot may show it
    up to 15 s late.
  - Idempotency: the same key and body returns the original claim (200,
    Idempotent-Replayed: true). The same key with a different body returns 409
    IDEMPOTENCY_MISMATCH.
  - Errors: {error:{code,message,field?}}.
    - 400 VALIDATION
    - 401 UNAUTHORIZED
    - 404 NOT_FOUND
    - 409 IDEMPOTENCY_MISMATCH
    - 429 RATE_LIMITED (retryAfterMs)
    - 500/503 SERVER
    - 504 TIMEOUT (outcome unknown)
  - Not covered by the docs (to go under Assumptions):
    - A fee equal to or larger than the amount; the client also requires amount 
      > fee.
    - There's no endpoint that lists claims, so the app has to remember its own
      claim ids.

    - Actual rate-limit numbers.
    - Max uses the snapshot's available, so the server may still reject it.

  lags up to 15 s, and a failed claim returns it to available.                  
  Give me 2-3 approaches with trade-offs for both complaints. Also the same for 
  the unknown-outcome case (timeout/504 on POST). Don't write code yet, I'll

⏺ 1. Balance right after a claim is submitted

  Two facts shape this:
  - asOf and the claim's createdAt both come from the server's clock. So "does
    this snapshot already include my claim?" is an exact check: asOf >= 
    createdAt. No guessing from the phone's clock.
  - The server checks available live, so a second claim can never take more than
    you have. The real harm in complaint 1 is a second claim the user didn't
    want, not an overdraft.

  A. Show the server's snapshot as-is, plus a "Claim in progress" card
  - Home keeps showing the snapshot unchanged. A card above the asset says
    "Claiming 0.5 ETH, pending". The Claim button for that asset is disabled
    while the claim is pending.
  - Complaint 1 ("didn't change, claimed again"): the numbers stay wrong for up
    to 15 s. The card and the disabled button stop the second tap, but the user
    still sees old numbers.
  - Complaint 2 ("dropped, then jumped back"): never happens. Numbers only move
    when the server moves them.
  - Cost: least code and nothing to reconcile, but the numbers feel stale.

  B. Adjust the balance in the app immediately, then hand back to the server
  - The moment the POST returns 201/200, the app shows available − amount and
    claiming + amount for that asset, tracked by claim id.
  - The app stops adjusting once a snapshot arrives with asOf >= 
    claim.createdAt, because the server's number already includes the claim.
  - If the claim fails, the adjustment is dropped and refreshed balances are
    fetched. The card says "Claim failed: <failureReason>. 0.5 ETH is back in
    available."
  - Complaint 1: fixed. The balance drops at once.
  - Complaint 2: the only jump back is a real failure, and it comes with an
    explanation. A sloppy version would subtract twice and then jump; the asOf
    check prevents that.
  - Cost: the most logic, but every input is a server value, and it's easy to
    unit-test as a pure function: (snapshot, my claims) → displayed balance.

  C. Mark the asset as "updating" until the server catches up
  - That asset's available/claiming show a greyed "Updating…" with the previous
    value struck through, until asOf >= createdAt. That usually takes 15 s or
    less. Claim is disabled meanwhile.
  - Complaint 1: fixed. The user can't claim again and can see something is
    happening.
  - Complaint 2: fixed. No number appears that later reverses.
  - Cost: the balance is effectively hidden for up to 15 s on every claim, which
    feels slow. On a failed claim it still has to show the amount coming back.

  My pick: B. It answers complaint 1 directly. It keeps complaint 2 to real
  failures, which come with an explanation. It also gives the claim form a
  correct "Max" right after a claim. Add A's disabled button while a claim for
  that asset is pending as a second guard.

  2. Unknown outcome (network error, timeout, 500/503/504 on POST)

  One catch first: re-sending with the same key is not a read-only status check.
  If the first request never reached the server, the re-send creates the claim.
  That matches what the user confirmed, so it's fine, but the wording on screen
  should say "Retry", not "Check". Also note:
  - With no list-claims endpoint, the only exact way to resolve an unknown claim
    is a re-send with the same key.
  - The docs don't say how long the server remembers a key. That goes under
    Assumptions.

  A. Retry quietly with the same key
  - After an unknown outcome, re-send with the same key 2–3 times (about 1 s, 3
    s, 7 s apart; on 429 wait retryAfterMs). The screen says "Submitting…
    confirming result".
  - Most blips resolve without the user ever seeing an error.
  - Risk: during a long outage the user waits about 10 s or more and then still
    needs a fallback screen.

  B. Show the user it's unknown and let them decide
  - Screen: "We couldn't confirm your claim of 0.5 ETH. It may or may not have
    gone through." Buttons: Retry (same key, safe) and Close.
  - Close keeps the saved claim attempt, so Home keeps showing a "Claim not
    confirmed: Retry" banner, even after a reload.
  - The asset's Claim button stays disabled until the outcome is known, so no
    new key can ever be created for that attempt.
  - Clear and honest, but it puts a scary choice in front of the user for every
    short network blip.

  C. Treat it as a probable claim in the balance
  - Same as B, but Home also shows the amount as "claiming (unconfirmed)", using
    the balance adjustment from 1-B.
  - Protects against complaint 1, because the user doesn't think the money is
    still free.
  - Risk: if the claim never actually landed, the balance later jumps back,
    which is complaint 2 again, and this time it isn't a real failure. The way
    to reverse it is to show a definite result: once a retry returns 201 or 4xx,
    resolve it explicitly.

  My pick: A, then B.
  - Retry quietly a few times first, then fall back to B's screen and the saved
    banner.
  - Don't adjust the balance for an unknown claim (reject C). Showing money as
    moved before the server confirms it is exactly what makes complaint 2
    happen.
  - What resolves it:
    - 201/200 → it becomes a normal claim (1-B adjustment, polling).
    - 4xx such as VALIDATION/insufficient → a definite "no claim was created",
      saved attempt cleared, message shown.
    - 409 → shouldn't happen, because the body is saved with the key. If it
      does, show it as an error and keep the saved attempt for support.

  Which do you pick: 1 A, B or C; 2 A, B, C or A then B? Once you choose, I'll
  write the reasoning and the rejected options into the Decisions section of
  NOTES.md.
